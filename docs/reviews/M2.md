### `/__ui` `edge-text`: a probe defect, fixed in the probe (round 3)

The FAIL said "An Artist With A Long Name, Fe…" sat 4 px from the right edge at 390.

- **What the rule measures.** `probe.mjs` builds one box per text node from
  `Range.selectNodeContents(node).getBoundingClientRect()`, then flags boxes within 12 px (phone)
  or 16 px of the edge. A Range's bounds are the laid-out glyphs, and **they ignore overflow
  clipping**.
- **The component.** The media track row's artist line (`.track-sub`) is `white-space: nowrap;
  overflow: hidden; text-overflow: ellipsis`, per §9.3.
- **Measured at 390 in Chromium:** element box and clip box x = 96–288. The text node's Range is
  x = 96–380, which is the untruncated string. The Range ends 10 px from the edge in my run; the
  audit's run reported 4 px.
- **Pixels.** I screenshotted the text line's band (y = 336–353, full width). Every pixel in the
  12 px band at the right edge is page background (`#0a0b0d`), and the rightmost painted pixel is
  x = 345 (the duration). On screen the artist line ends in an ellipsis 102 px from the edge.
  **No user can see text near the edge.**
- **Exception mechanisms.** The skill has none that is narrow enough. `--allow edge-text` switches
  the rule off for the whole page. `data-ui` is for interface fragments on marketing pages (it
  would be misuse here, and it caused round 1's `ui-wrapper` FAIL). The marquee/ticker class
  exclusion would be a hack.
- **Fix (in the skill, not in ECHO).** After the rule's existing on-screen filter, each text box is
  intersected with every ancestor whose `overflow-x` is not `visible`, and the edge test runs on
  that visible box. The probe's own `overflow` rule already reasons this way (`clippedByAncestor`).
  The change touches only `edge-text`, and the set of flagged texts can only shrink: a visible box
  is never wider than the raw box. Fixtures at 390 show the check is not weakened:

  |---|---|---|
  | `plain`: unclipped text 4 px from the edge | FAIL | FAIL |

### CI's e2e job, reproduced: it would have failed

There is no remote, so GitHub CI has never run. I reproduced the e2e job in
`mcr.microsoft.com/playwright:v1.64.0-noble` (Ubuntu 24.04, the browsers @playwright/test 1.64.0
pins) with Node 24.22.0, `CI=1`, `pnpm install --frozen-lockfile` and the full suite, on a copy of
the tree.

- **Result on the old setup: 13 failed.** These were 12 visual baselines (`library-dock-*`,
  `album-*`, `buttons-*`, `sheet-*`; 10–216 px each) and the new DS-02 check at 390 (Ubuntu measured
  1.6–3.7% where this machine measured ≤ 0.22%).
- **Cause, from the pixels:** Ubuntu's Chromium draws text with **subpixel (LCD) antialiasing**,
  orange and blue fringes on every glyph (enlarged crop inspected). This machine draws greyscale.
  The fringes come from the host's font settings, not from the design.
- **Fix:** `--disable-lcd-text` in the Chromium launch args (`playwright.config.ts`), so text is
  greyscale on every machine. With it, the **existing baselines pass unchanged in Ubuntu** (no
  baseline was re-made and no tolerance changed), and the colour shares match this machine to two
  decimals.
- **Firefox WebGL.** Headless Firefox has no WebGL 2 on either machine. In the Ubuntu image, under
  `xvfb-run`, it gets WebGL 2 on Mesa llvmpipe with `WEBGL_lose_context` (probe). With Xvfb, the 11
  Firefox Stage tests that skipped everywhere now run: context loss and recovery, hidden tab, tier
  cap and resize, reduced motion, loop release, dither, `?frame/?track/?fixture`, and the scrim fade.
- **A flaky error this exposed, root-caused:** under Xvfb, 7 of 192 runs logged a Firefox console
  error "downloadable font: download failed … status=2152398850" (`NS_BINDING_ABORTED`). The `with
  WebGL 2` tests load `/library` in `beforeEach` and then `goto` another URL; that navigation
  aborted the first page's font download. `document.fonts.ready` is not a fix, because it resolves at
  once if the load has not started. The `beforeEach` now awaits `document.fonts.load('16px "Mona
  Sans"')`. After the fix: **180/180** in a 15× repeat, with no aborts. App probes (30 sequential, and
  60 under 4× parallel load, navigating in-app) never aborted and always ended with Mona Sans loaded,
  so it was not an app defect.
- **CI change** (`.github/workflows/ci.yml`): the e2e job runs in that image, pinned by digest, as
  user 1001 with `--ipc=host`, and runs `xvfb-run -a pnpm test:e2e`. The separate
  `playwright install --with-deps` step is gone (the image has the browsers).
- **Local equivalent:** `scripts/e2e-container.sh [playwright args]` runs the same job on a copy of
  the tree. It needs Docker's `--init`, because as PID 1 `xvfb-run` never gets Xvfb's ready signal
  and hangs (found and fixed while testing the script).
- **Final runs on this tree:** container script **250 passed, 0 failed, 66 skipped**; host
